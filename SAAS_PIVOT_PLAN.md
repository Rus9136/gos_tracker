# План: пивот в SaaS — все лоты, гейтированный LLM

Дата: 2026-07-28. Статус: **фазы A и B выполнены** (A — 2026-07-28, коммиты
WP1–WP5: verticals.py, ListingHit.enstru_code, rename-миграция
`c1a2b3d4e5f6`, watchlist-заглушка, снятие IT-фильтра + detail_scope +
docs-гейт; правило #24 в CLAUDE.md. B — 2026-07-29, см. отступления в
разделе фазы). Фазы C–E — не начаты.

## Цель

Из личного IT-трекера — платформа для продажи по подписке: храним **все**
лоты goszakup (товары/услуги/работы), пользователи покупают доступ, видят
аналитику по своей нише, получают новые лоты и уведомления, строят
семантические запросы. Дорогие стадии (документы, LLM) включаются не для
всего рынка, а по **watchlist**: вертикали с подписчиками + пре-фильтры
пользовательских запросов.

## Что уже посчитано (обоснование решений)

- «Только IT» держится на `if cat is None: continue` в трёх листинг-циклах
  (`jobs/run_preset.py:453`, `queue/actors.py:323` api_daily,
  `queue/actors.py:455` listing_actor). Всё остальное гейтится отдельно.
- Листинг всех лотов **не добавляет запросов** к goszakup — api_daily и так
  получает весь поток за окно, фильтр стоит после. Поток ~2 тыс. лотов/день
  (~700-800k/год), IT ≈ 9%.
- Детализация всех объявлений через OWS: ~1000-2000 объявлений/день × 1 rps
  = 20-35 мин/сутки. **Только через API** — HTML-фолбэк на полном рынке
  математически не проходит (20+ часов), при `api_degraded` детализация
  должна сужаться до watchlist.
- LLM для детализации не нужен (чистый fetch структурированных полей).
  LLM — только чтение ТЗ.
- Экономика LLM (факт из `llm_calls`, цены платного Cerebras): анализ ТЗ
  ~$0.0016/лот (5.7k prompt + 0.2k completion), матч ~$0.00024/пара.
  Весь рынок целиком ≈ $105/мес (p90 $190), watchlist 20% ≈ $20-40/мес,
  матчинг ≈ $2/мес на активного пользователя. Анализ лота делается один раз
  и переиспользуется всеми (идемпотентность уже есть) — главный рычаг маржи.

## Ключевые дизайн-решения

1. **Таксономия — «вертикали»** (кураторские отрасли: IT, Медицина, Стройка,
   Мебель, Продукты, Клининг, Охрана, СИЗ/одежда, Транспорт, Обучение, …),
   каждая маппится на префиксы кода ЕНС ТРУ (первые 2 цифры = раздел КПВЭД:
   26/58/61/62/63 → IT, 21/32.5/86 → медицина, 41-43 → стройка, 31 → мебель…)
   плюс keyword-фоллбэк. Живут в коде (`classify/verticals.py`, паттерн
   `classify/it.py`) — тестируемо и версионируемо; админ-UI редактирования
   НЕ делаем (не добавлять фичи без необходимости). Пользователю продаём
   вертикали, не голое КТРУ-дерево.
2. **`Lot.it_category` → `Lot.category`** (rename-миграция + генерализация
   значения: слаг вертикали, NULL = «прочее»). Аналогично
   `User.it_categories` → `User.categories`, `Preset.it_categories` →
   `Preset.categories`. Один болезненный рефакторинг сейчас дешевле двух
   параллельных полей навсегда.
3. **Watchlist = f(подписки, запросы)**, не отдельная таблица. Функция
   `should_analyze(session, lot) -> bool`:
   (а) `lot.category` входит в вертикали хотя бы одного активного
   пользователя; ИЛИ (б) лот проходит пре-фильтр хотя бы одного активного
   `UserQuery`. Результат кешируется в Redis (TTL ~5 мин) — вызов идёт на
   каждый лот листинга.
4. **Пре-фильтр запроса** — в уже существующем `UserQuery.compiled_filters`
   (JSON, сейчас NULL): `{code_prefixes: [...], keywords: [...],
   max_amount: ...}`. Запрос БЕЗ пре-фильтра не триггерит анализ — матчится
   только по уже проанализированным лотам (иначе пустой запрос = анализ
   всего рынка). В UI `/queries` — поля пре-фильтра рядом с NL-текстом;
   опционально позже: LLM-компиляция NL-текста в пре-фильтр.
5. **Детализируем ВСЕ лоты** (ради дедлайнов/организаторов/аналитики), но
   только пока жив API-путь; документы и LLM — только watchlist.
6. **Биллинг стартуем ручным** (KZ B2B: счёт на оплату / Kaspi перевод,
   админ активирует подписку руками в `/users`). Stripe/автосписание —
   отдельная фаза после первых клиентов. Тариф на старте один, лимиты:
   число вертикалей, число запросов, Telegram вкл/выкл, автоподача —
   премиум.

3. Rename-миграция `it_category`→`category` (+ данные: 4 старых значения →

### Фаза B — вертикали в UI и scope — ✅ выполнена 2026-07-29

`cat_tag` принимает слаг; дашборд «По вертикалям» с дриллдаунами и «Прочее»;

честные подписи «лоты в вертикалях». **Отступление:** self-serve редактор

1. `web/app.py`: `IT_CATEGORIES` → `VERTICALS` из classify; фильтры

### Фаза C — watchlist и пре-фильтры запросов

1. `scope.py` или новый `watchlist.py`: `should_analyze(session, lot)` —
   реальная реализация (вертикали активных пользователей ∪ пре-фильтры
   активных запросов), Redis-кеш. «Активный пользователь» = есть строка
   в users и (после фазы D) живая подписка.
2. `UserQuery.compiled_filters`: UI-поля (префиксы кодов, ключевые слова,
   макс. сумма), валидация; правка пре-фильтра бампает `version` как и
   правка текста.
3. Fan-out: новый проанализированный лот уже раздаётся
   `enqueue_matches_for_lot` — добавить учёт пре-фильтра при отборе
   запросов (сейчас отбор только по scope).
4. Обратный триггер: лот прошёл пре-фильтр запроса, но не был в watchlist
   на момент прохода листинга → анализ добирается следующим daily
   (идемпотентно). Отдельный «догоняющий» механизм не строим (KISS);
   создание нового запроса зовёт существующий backfill, который при
   отсутствии анализа ставит лот в `goszakup_llm`.
5. Бамп `MATCHER_VERSION` не нужен (промпт не меняется).

### Фаза D — SaaS-обвязка

1. Модель подписки: `User.plan` (слаг), `User.paid_until` (date),
   `User.is_active` property. Истёкшая подписка = read-only заглушка
   «продлите» (данные не удаляем, из watchlist выпадает).
2. Лимиты тарифа в коде (`config` или `plans.py`): вертикали ≤N,
   запросы ≤M, Telegram, автоподача. Проверки в формах scope/queries.
3. Саморегистрация `/register` (email+пароль, без верификации на старте;
   новый юзер = триал X дней, узкий лимит) ИЛИ решение «регистрирует только
   админ» — см. открытые вопросы.
4. `/users` (admin): продление подписки, план, заметки по оплате.
5. Уйти с Cerebras free-tier на платный ключ ДО первых клиентов
   (`GZ_LLM_*` не меняются, только ключ/лимиты; health-check уже сторожит).
6. Лендинг-витрина — вне этого репо (salemsoft.kz), в план не входит.

### Фаза E — история и аналитика (продаваемая ценность)

1. Бэкофилл листинга истории через OWS по окнам `lastUpdateDate` (скрипт по
   образцу `backfill_start_dates.py`; месяцы → годы, докуда позволит API).
   Только листинг-поля; детали/документы истории НЕ качаем.
2. Договоры/победители/заявки для истории — теми же `contracts_sync` /
   `bids_sync` с расширенным горизонтом (у них вход — известные лоты).
3. Страницы аналитики по вертикали/нише: топ-заказчики, топ-поставщики,
   динамика сумм, конкуренция (среднее число заявок), демпинг (из
   `lot_bids`). Всё — SQL по своей БД, к goszakup не ходит.
4. При приближении к 10M строк — посмотреть на партиционирование `lots`
   по годам; до ~2-3M не трогать (индексы уже есть).

## Что НЕ делаем (осознанно)

- Не анализируем LLM-ом весь рынок «потому что дёшево» — рано; watchlist
  снимает нагрузку на v3bl (документы) и лимиты провайдера.
- Не строим админ-UI редактирования вертикалей — таксономия в коде.
- Не привязываем лоты к пользователям FK-ами — read-time scope (правило #15)
  остаётся ядром multi-tenant.
- Не детализируем историческую массу и HTML-ом не ходим по полному рынку.
- Не делаем автосписание платежей на старте.
